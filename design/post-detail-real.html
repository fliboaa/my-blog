智能体自动化

Hermes Agent 自动化原理揭秘：四层架构实现全自动博客发布

Hermes 四层架构

Hermes 的能力不是平铺的，而是分层抽象。每一层专注一件事，层与层之间靠清晰的接口连接。

  • 编排层：Cron 调度、任务编排、错误重试。负责"什么时候做什么"
  • 技能层：可复用能力（clip-workflow / lark-doc / hindsight）。负责"怎么做"
  • 安全层：Tirith 安全策略、权限控制。负责"能不能做"
  • 应用层：最终落地的应用（发布博客 / 同步 GitHub）。负责"做了什么"

编排层：Cron 调度

Cron 是自动化的总控。它按时间触发任务，传递参数，处理错误。关键特性：

cronjob(
  action="create",
  schedule="0 9 * * 1-5",  # 工作日 9 点
  prompt="生成每日工作总结",
  skills=["daily-review"]
)
Cron 启动的是独立进程，不受主会话约束。这是能力，也是洞。

技能层：可复用能力

技能是封装好的能力，通过 frontmatter 约定输入输出。比如 clip-workflow 技能定义了完整的剪藏链路：抓取 → 生成笔记 → 写入飞书 → 清理临时文件。

技能的优势是复用。同一个剪藏能力，可以用于博客发布、知识库归档、资料收集。

安全层：Tirith 安全策略

Tirith 是 Hermes 的安全层，拦截危险操作。比如：

  • no_agent=True 的 Cron 任务不受约束
  • 发布到外部渠道需要批准
  • 删除不可恢复数据前会确认
⚠️ 关键点

no_agent=True 启动的独立进程完全绕过 Tirith——这是实现无人值守自动化的必要条件，但也带来了静默失败的风险。

no_agent=True 的能力与洞

no_agent=True 的 Cron 任务有两个特性：

  1. 能力：不受 Tirith 约束，可以执行发布、同步、清理等操作
  2. 洞：脚本错误不反馈到 AI，静默失败

要利用能力、规避洞，需要补两件事：

  1. 脚本可观测性：脚本内部捕获错误，写入日志，失败时主动通知
  2. 读回验证：脚本返回结果后，Agent 必须读回验证（而不是相信返回的"成功"）

常见陷阱

在实践自动化时，我踩过这些坑：

  1. 依赖路径：脚本依赖的路径在 Cron 环境下不同，必须用绝对路径
  2. 权限继承：Cron 任务不继承用户的 shell 环境变量，需要显式配置
  3. 静默失败：脚本 exit 0 但实际没执行成功——必须加验证逻辑

行动建议

如果你想在 Hermes 里做自动化，这三步必须先做：

  1. 盘点现有 cronjob：标注哪些是 no_agent、哪些含网络/发布操作——确认没有越 SOUL「公开发布必须批准」红线
  2. 补可观测性：在 no_agent 脚本里加日志、错误捕获、失败通知
  3. 确认凭证安全：Token 用 SSH 而非 HTTPS——Token 会被 Tirith 脱敏导致失败

自动化不是"写个 Cron 就完事"，而是四层架构的协同设计。每一层都要考虑：输入、输出、错误处理、安全约束。
